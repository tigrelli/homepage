# 개인 홈페이지 & 블로그 운영방안 · 기술스택

대상: 정적 HTML 기반 개인 홈페이지 + 블로그 (PM이 기획/검수, Claude Code가 HTML 생성·수정)
핵심 요구사항: 블로그 글마다 방문자 댓글 기능 필요

---

## 1. 전체 구조

서버·DB 없이 정적 파일만으로 운영하는 것을 기본 전제로 합니다. Claude Code가 결과물로 순수 HTML(+CSS/JS)을 만들기 때문에, 별도 백엔드를 두지 않아도 되는 구조가 지금 워크플로우와 가장 잘 맞습니다. 댓글처럼 서버 저장이 필요한 기능만 외부 서비스를 붙여서 해결합니다.

```
repo/
├── index.html              # 홈페이지
├── about.html               # 소개 상세
├── portfolio.html           # 포트폴리오
├── blog/
│   ├── index.html          # 블로그 목록
│   ├── posts.json          # 글 메타데이터 인덱스 (제목/날짜/카테고리/태그/파일경로)
│   ├── categories.json     # 카테고리 고정 목록
│   └── posts/
│       ├── 2026-08-10-xxx.html
│       └── ...
├── assets/
│   ├── images/
│   └── css, js 공통 리소스
└── docs/                   # 기획 문서 (현재 폴더)
```

## 2. 운영 워크플로우

**홈페이지 수정**: PM이 수정할 내용을 Claude Code에 의뢰 → Claude Code가 해당 HTML을 직접 수정 → 로컬(또는 미리보기)에서 확인 → git commit/push → 자동 배포.

**블로그 발행**: PM이 글 내용(텍스트나 마크다운 초안)을 전달 → Claude Code가 디자인 적용 + 필요한 이미지 생성/삽입까지 포함해 `blog/posts/`에 새 HTML 파일 생성 → `posts.json` 인덱스에 새 글 메타데이터 추가 → git push → 배포. 목록 페이지는 `posts.json`을 읽어 JS로 렌더링하므로 목록 HTML을 매번 손으로 고칠 필요가 없습니다.

이 흐름이 성립하려면 사이트가 **git 저장소 기반**이어야 합니다. Claude Code의 파일 생성·수정 결과를 그대로 커밋하고 push하면 배포까지 이어지는 구조가 관리 부담이 가장 적습니다.

## 3. 카테고리 구조

블로그 글마다 카테고리를 하나씩 갖도록 합니다 (예: 기술, 취미). 카테고리는 자주 바뀌는 값이 아니므로 고정 목록으로 별도 관리하고, 각 글은 그중 하나를 참조하는 방식이 가장 관리가 쉽습니다.

### 3.1 데이터 구조

`posts.json`의 각 글 항목에 `category` 필드를 추가합니다.

```json
{
  "slug": "2026-08-10-ai-pm-note",
  "title": "...",
  "date": "2026-08-10",
  "category": "기술",
  "tags": ["AI", "PM"],
  "summary": "...",
  "thumbnail": "/assets/images/xxx.webp"
}
```

`category`는 목록 필터·배지 표시용 단일 분류이고, `tags`는 검색 보조용 다중 태그로 용도를 분리합니다. 카테고리 고정 목록은 `blog/categories.json`에 별도로 정의해서 목록 페이지와 글 상세 템플릿이 공통으로 참조하게 합니다.

```json
["전체", "기술", "취미"]
```

새 카테고리가 필요하면 이 파일에 값 하나만 추가하면 됩니다.

### 3.2 UI

기존 와이어프레임(`blog-wireframe.html`)에 이미 카테고리 칩 UI가 있습니다. 이 칩들을 `categories.json` 기반으로 렌더링하고, 클릭 시 `posts.json`을 `category` 값으로 필터링해 목록을 다시 그리는 클릭 핸들러를 붙이면 됩니다. 글 상세 페이지에는 카테고리 배지를 하나 표시하고, 클릭하면 해당 카테고리로 필터링된 목록으로 이동하게 합니다.

### 3.3 운영

Claude Code가 새 글을 만들 때 PM이 지정한 카테고리 값을 `posts.json`에 그대로 넣습니다. `categories.json`에 없는 값은 쓰지 않는 규칙만 지키면, 오탈자나 중구난방한 분류가 쌓이는 것을 막을 수 있습니다.

## 4. 기술스택

| 영역 | 추천 | 이유 |
|---|---|---|
| 버전관리 | GitHub (리포지토리 1개) | Claude Code 결과물을 커밋 단위로 추적, 실수 시 롤백 용이 |
| 호스팅 | GitHub Pages | 정적 파일 push만으로 배포, 완전 무료, 별도 빌드 설정 불필요 |
| 배포 자동화 | GitHub Actions (선택) | push 시 자동 배포. 이미지 최적화 등 빌드 단계가 생기면 이때 추가 |
| 도메인 | 커스텀 도메인 연결 (선택) | 가비아/Cloudflare 등에서 구매 후 CNAME 연결, 연 1~2만원 |
| 이미지 | Claude Code가 생성 후 `/assets/images`에 저장, WebP 변환 | 별도 이미지 서버 불필요, 용량 관리만 신경 |
| 블로그 목록/검색 | `posts.json` 정적 인덱스 + 클라이언트 JS 필터링 | DB 없이 태그/날짜 검색 가능 |
| 댓글 | Supabase (Postgres + Edge Function) | 자체 소유 DB, 완전한 디자인·기능 커스터마이징, 무료 티어로 개인 블로그 트래픽 충분 |

호스팅 대안으로 Netlify·Vercel도 있으며 미리보기 배포, 폼 기능 등이 내장돼 있지만, 지금처럼 빌드 과정 없는 순수 HTML이면 GitHub Pages가 설정도 가장 단순하고 비용도 없어 우선 추천합니다.

**결정 (2026-08-10): GitHub Pages 확정.** Vercel(Hobby 플랜)과 비교 검토했습니다. 둘 다 무료로 커스텀 도메인·SSL을 지원하고 push 시 자동 배포되지만, Vercel Hobby는 상업적 이용을 금지하는 약관이 있고(단, 개인 포트폴리오·비상업 블로그는 허용 대상으로 명시돼 있어 지금 사이트는 문제없음), `vercel.json`으로 캐시 헤더·리다이렉트를 세밀하게 제어할 수 있다는 점이 GitHub Pages 대비 장점입니다. 반면 GitHub Pages는 이미 CLAUDE.md·진행현황.md 전체가 GitHub 저장소 기준 워크플로우로 짜여 있어 별도 계정 연동이 필요 없고, 방문객이 적은 지금 단계에서는 헤더 세밀 제어의 이점이 체감되지 않습니다. 도메인은 GitHub이 직접 판매하지 않으므로 가비아·Cloudflare Registrar 등에서 별도 구매 후 DNS만 GitHub Pages로 연결합니다. 트래픽이 늘어 캐싱·리다이렉트 제어가 필요해지면 정적 파일을 그대로 옮겨 Vercel로 전환할 수 있습니다.

## 5. 댓글 기능 — Supabase 자체 구현

정적 사이트에서 Supabase를 쓰면 별도 서버 없이도 자체 댓글 DB를 가질 수 있습니다. 읽기는 정적 HTML에서 Supabase JS client로 직접 조회하고, 쓰기(등록)만 Edge Function을 거쳐 스팸을 막는 구조입니다.

### 5.1 아키텍처

```
블로그 글 HTML (comments.js 공통 스크립트 포함)
   ├─ 댓글 목록 조회: Supabase JS client → comments 테이블 SELECT (anon key)
   └─ 댓글 등록: Supabase Edge Function 'submit-comment' 호출
                  ├─ Turnstile 토큰 검증
                  ├─ IP 해시 기준 rate limit 체크
                  └─ 통과 시 service role로 comments 테이블 INSERT
```

읽기는 공개 anon key로 직접 접근하고, 쓰기는 anon key로 테이블에 바로 넣지 않고 Edge Function을 한 번 거치게 해서 스팸/어뷰징을 걸러냅니다.

### 5.2 데이터베이스 스키마

```sql
create table comments (
  id uuid primary key default gen_random_uuid(),
  post_slug text not null,        -- posts.json의 글 식별자와 매칭
  author_name text not null,
  content text not null,
  parent_id uuid references comments(id),  -- 대댓글용, MVP에서는 생략 가능
  ip_hash text,                    -- rate limit용, 원본 IP는 저장하지 않음
  created_at timestamptz not null default now()
);

create index on comments (post_slug, created_at);
```

### 5.3 RLS(Row Level Security) 정책

```sql
alter table comments enable row level security;

-- 누구나 댓글 조회 가능
create policy "public read" on comments
  for select using (true);

-- 클라이언트(anon key)에서 직접 INSERT는 막는다 → Edge Function(service role)만 등록 가능
-- INSERT용 policy를 만들지 않으면 anon 역할은 기본적으로 거부됨
```

anon key는 SELECT만 허용하고, INSERT는 정책을 아예 만들지 않아 막아둡니다. 등록은 Edge Function 내부에서 service role key로만 수행되므로 브라우저에서 테이블에 직접 쓰는 경로 자체가 없습니다.

### 5.4 스팸 방지

- **Cloudflare Turnstile**(무료): 댓글 폼에 위젯 삽입, 제출 시 토큰을 Edge Function으로 전달해 서버 사이드에서 검증
- **IP 기반 rate limit**: Edge Function에서 IP를 해시해 최근 1분 내 등록 이력 확인 후 초과 시 거부 (원본 IP는 저장하지 않고 해시만 보관)
- **허니팟 필드**: 폼에 숨겨진 입력 필드를 추가해 봇이 채우면 자동 거부
- **길이 제한**: content 최대 글자 수 제한으로 스팸성 장문 도배 방지

### 5.5 Edge Function 흐름 (`submit-comment`)

1. 클라이언트: `supabase.functions.invoke('submit-comment', { body: { post_slug, author_name, content, turnstile_token } })`
2. Function 내부: Turnstile 토큰을 Cloudflare API로 검증 → IP 해시 rate limit 체크 → 입력값 검증(길이, 허니팟) → 통과 시 service role client로 INSERT
3. 성공 응답 후 클라이언트가 댓글 목록을 다시 조회해 화면 갱신

### 5.6 모더레이션

즉시 게시(post-moderation) 방식을 추천합니다. 댓글은 등록 즉시 노출되고, PM은 Supabase 대시보드의 Table Editor에서 직접 삭제·수정할 수 있어 별도 관리자 페이지를 만들 필요가 없습니다. 트래픽이 늘어 신고 기능이 필요해지면 `report_count` 컬럼을 추가해 일정 횟수 이상 신고된 댓글을 자동 숨김 처리하는 트리거를 붙이는 방식으로 확장하면 됩니다.

### 5.7 블로그 글 템플릿에 삽입

Claude Code는 새 글을 만들 때마다 아래 두 줄만 넣으면 됩니다. 실제 로직(목록 조회, 폼 렌더링, 제출)은 공통 파일 하나로 관리합니다.

```html
<div id="comments" data-post-slug="{{slug}}"></div>
<script src="/assets/js/comments.js" defer></script>
```

`comments.js`는 최초 1회만 작성하고, 이후 모든 글에서 재사용합니다.

## 6. 댓글 운영 정책

Turnstile + rate limit + 허니팟 조합으로 자동화된 스팸을 1차로 걸러내고, 통과한 댓글은 즉시 게시됩니다. 부적절한 댓글은 Supabase Table Editor에서 직접 삭제하며, 반복적으로 문제를 일으키는 IP는 `ip_hash` 기준으로 Edge Function 단계에서 차단 목록에 추가할 수 있습니다. 새 댓글 알림이 필요하면 Supabase Database Webhook을 설정해 INSERT 발생 시 이메일(Resend 등)이나 Slack으로 알림을 보내도록 확장할 수 있습니다.

## 7. 실행 로드맵

1. GitHub 리포 생성 → GitHub Pages 연결 → 기존 와이어프레임(`blog-wireframe.html`, `portfolio-wireframe*.html`) 기반으로 실제 홈페이지 HTML 퍼블리싱
2. 블로그 목록/상세 템플릿 확정, `posts.json`·`categories.json` 구조 설계, 카테고리 필터 UI 구현
3. Supabase 프로젝트 생성 → `comments` 테이블·RLS 정책 적용 → `submit-comment` Edge Function 작성·배포 → Cloudflare Turnstile 발급 → `comments.js` 공통 스크립트 작성 → 상세 템플릿에 삽입, 테스트 댓글로 동작 확인
4. (선택) 커스텀 도메인 연결
5. 운영 단계 진입: PM이 홈페이지 수정/블로그 초안을 Claude Code에 의뢰 → 결과 검수 → push, 댓글은 Supabase 대시보드에서 주기적으로 모니터링

## 8. 예상 비용

GitHub Pages 무료. Supabase 무료 티어(DB 500MB, Edge Function 월 50만 호출)로 개인 블로그 트래픽은 충분히 감당 가능하며, Cloudflare Turnstile도 무료입니다. 커스텀 도메인을 쓰지 않으면 사실상 비용 없이 운영 가능하며, 도메인을 쓰더라도 연 1~2만원 수준입니다.

## 9. SEO·메타 운영

SEO는 호스팅과 무관하게 파일 자체로 관리하는 영역입니다. GitHub Pages든 Vercel이든 아래 요소들을 직접 채워 넣어야 검색에 노출됩니다.

### 9.1 페이지별 필수 요소
모든 페이지(홈페이지 3종 + 블로그 목록/상세)에 `<title>`, `<meta name="description">`, `<link rel="canonical">`를 페이지마다 다르게 채웁니다. Open Graph(`og:title`, `og:description`, `og:image`, `og:url`)도 함께 넣어 카카오톡·SNS 공유 시 미리보기가 제대로 뜨게 합니다.

### 9.2 사이트 전역 파일
루트에 `sitemap.xml`, `robots.txt`를 둡니다. 홈페이지 3종은 고정 URL이라 한 번 넣으면 되지만, 블로그 글은 발행할 때마다 `sitemap.xml`에 새 URL을 추가해야 합니다. `posts.json` 갱신과 같은 타이밍에 Claude Code가 함께 처리하는 것을 원칙으로 합니다(빌드 과정이 없어 자동 생성이 안 되므로 수작업 갱신 필요).

### 9.3 구조화 데이터
블로그 글 상세 템플릿에 JSON-LD로 `BlogPosting` 구조화 데이터(제목, 작성일, 저자, 이미지)를 넣어 검색 결과에 리치 스니펫이 뜰 가능성을 높입니다.

### 9.4 검색엔진 등록
Google Search Console과 네이버 서치어드바이저 양쪽에 사이트를 등록합니다. 둘은 크롤링 정책이 달라 하나만 등록하면 다른 한쪽 검색에는 거의 노출되지 않습니다. 각각 사이트 소유 확인(메타태그 또는 DNS)과 `sitemap.xml` 제출이 필요합니다.
